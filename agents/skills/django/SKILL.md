# Django

Conventions that apply to any Django project. These are the ones that get missed.

## Migrations

Before committing anything that touches a model:

```bash
python manage.py makemigrations --check --dry-run
```

Non-zero exit means a migration is missing — generate it and include it in the same commit. A model change without its migration is a broken deploy, not a follow-up.

Review generated migrations before committing. Autogenerated names are fine; autogenerated `RunPython` stubs and unintended field drops are not.

## Bulk Writes Bypass Everything

Queryset `.update()` and `.delete()` go straight to SQL. They do not call `save()`, do not fire `pre_save`/`post_save`/`pre_delete`, do not write audit history rows (django-simple-history and equivalents), and do not dispatch per-object tasks.

Use them only when you have confirmed none of that is expected. Otherwise iterate and `save()`:

```python
# Wrong when any of the above applies
Order.objects.filter(status="pending").update(status="processing")

# Right
for order in Order.objects.filter(status="pending").iterator():
    order.status = "processing"
    order.save(update_fields=["status"])
```

Same reasoning for `bulk_create` and `bulk_update` — both skip signals.

When iterating is genuinely too slow, say so and bound the batch explicitly rather than switching silently to a bulk write.

## Transactions

- Side effects that must not fire on rollback — emails, task dispatch, webhooks, external API calls — go in `transaction.on_commit()`.
- Commit inside the lock that protects the rows being written, not after releasing it.
- `select_for_update()` needs an enclosing `atomic()` block; without one it silently does nothing useful.
- Nested `atomic()` creates a savepoint, not a new transaction. An inner rollback does not roll back the outer block.

## Queries

- Fix N+1 with `select_related` (FK/one-to-one) or `prefetch_related` (reverse FK/M2M).
- Never raise a test's expected query count to make it pass — the count going up is the bug report.
- Bound every unbounded read. `.iterator()` for large scans, explicit slicing elsewhere.
- `.exists()` over `len(qs)`, `.count()` over `len(qs)` when the rows aren't needed.

## Tests

- Use the project's existing factories and fixtures; check `conftest.py` before writing new ones.
- `assertNumQueries` / `django_assert_num_queries` around code paths where N+1 regressions matter.
- Migrations are code — when a data migration has non-trivial logic, test it.

## Project Setup

- Package manager per `pyproject.toml`: `[tool.poetry]` → poetry, `uv.lock` → uv, neither → pip.
- Find the settings module and the test runner config before assuming `manage.py test` vs pytest-django.
